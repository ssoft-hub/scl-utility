# Any view

Невладеющее представление только для чтения над `std::any` или типизированным
lvalue.

- Заголовок: `#include <scl/utility/any/any_view.h>`

## Обзор

`scl::any_view` относится к `std::any` так же, как `std::string_view` — к
`std::string`: он ссылается на существующее значение, не копируя его, поэтому
функция может принимать разнородный аргумент для чтения без затрат на выделение
памяти. Представление занимает два указателя и тривиально копируемо.

Представление ссылается либо на сам типизированный объект, либо на `std::any`,
внутри которого объект лежит. В первом случае тип известен на этапе компиляции —
его задаёт [`scl::type_key`](../meta/type_key.md), — поэтому RTTI не нужен,
а `type_name()`, `type_key()`, `has_value()` и само конструирование вычисляются
на этапе компиляции. Во втором случае каждое приведение делегируется
`std::any_cast`; поскольку сам `std::any` связан с RTTI, соответствующий
конструктор при `-fno-rtti` исчезает. Это убирает только собственную перегрузку
библиотеки — некоторые стандартные библиотеки объявляют `std::any` и без RTTI.
Если такой объект попадёт в конструктор для типизированного значения, он свяжется
через прямую ссылку: `type_name()` по-прежнему сообщит `"std::any"`, но `any_cast`
объект внутри уже не развернёт.

Доступ — только для чтения. `scl::any_cast` возвращает либо копию значения, либо
`const`-lvalue-ссылку; приведение к не-`const`- или rvalue-ссылке некорректно, потому что
представление не даёт доступа на запись к наблюдаемому объекту.

Представление не владеет объектом и не продлевает его время жизни. Оно
действительно лишь пока жив этот объект — та же оговорка, что и у
`std::string_view`.

## Возможности

- Невладеющее, только для чтения, шириной в два указателя, тривиально копируемо
- Ссылка на любое типизированное lvalue, без зависимости от RTTI
- Ссылка на `std::any` с делегированием `std::any_cast` (только в сборках с RTTI)
- Запросы идентичности `type_name` / `type_key` / `has_value` — `constexpr` на C++20
- Приведение через указатель `any_cast<T>(view*)` — `noexcept`, null при несовпадении
- Приведение через ссылку/значение `any_cast<T>(view&)` — бросает `scl::bad_any_cast` при несовпадении
- Неявное преобразование из `std::any`, поэтому один `any_cast` обслуживает оба случая

## Справочник по API

### Конструирование

```cpp
std::string text{"Hello Any!"};

scl::any_view empty{};      // не ссылается ни на какой объект
scl::any_view raw{text};    // ссылается на lvalue напрямую
scl::any_view alias = raw;  // тривиально копируемо
```

Принимаются только lvalue; привязка к rvalue привела бы к висячей ссылке и
отклоняется. При включённом RTTI `std::any` преобразуется неявно, и
представление ссылается на него:

```cpp
std::any boxed{text};
scl::any_view over_any{boxed};   // ссылается на std::any (только в сборках с RTTI)
```

`std::any` в форме rvalue также отклоняется, поэтому представление не переживёт
свой источник.

### Наблюдение

```cpp
std::string text{"Hello Any!"};
scl::any_view raw{text};

raw.has_value();   // true
raw.type_name();   // std::string_view с именем std::string; точное написание
                   // даёт компилятор, напр. "std::basic_string<char>"
raw.type_key();    // scl::type_key const *, идентифицирующий std::string
```

`has_value()` возвращает `false` для пустого представления и для представления
над пустым `std::any`. `type_name()` возвращает `std::string_view` с именем типа,
известным на этапе компиляции: имя самого типа, когда представление ссылается на
объект, и `type_name<std::any>()`, когда на `std::any` — то есть имя обёртки, а
не лежащего внутри типа.

`type_key()` возвращает указатель, а не ссылку: [`scl::type_key`](../meta/type_key.md) —
идентичность, у которой нет пустого значения, поэтому пустое представление
возвращает `nullptr`, и все три состояния остаются различимыми. Ненулевой результат —
ровно тот объект, который возвращает `scl::type_key_of<T>()`, поэтому сравнение с
ним стоит одно сравнение указателей, а инвариант `type_key()->name() == type_name()`
выполняется всегда:

```cpp
raw.type_key() == &scl::type_key_of<std::string>();   // true
scl::any_view{}.type_key();                           // nullptr
```

Тип, лежащий внутри `std::any`, определяйте через
`any_cast<T>` с самим этим типом `T`, а не через `any_cast<std::any>` — он
спрашивает «лежит ли внутри ещё один `std::any`» и обычно даёт `nullptr`.

### Приведение

Форма с указателем возвращает `const`-указатель при совпадении типа и `nullptr`
в противном случае. Она никогда не бросает исключений:

```cpp
if (auto const * s = scl::any_cast<std::string>(&raw))
    use(*s);   // без копирования
```

Форма со ссылкой возвращает объект по значению или по `const`-ссылке и бросает
`scl::bad_any_cast` при несовпадении. Результат-`const`-ссылка привязывается без
копирования; не-`const`- или rvalue-ссылка некорректна:

```cpp
std::string copy = scl::any_cast<std::string>(raw);                 // копия значения
std::string const & ref = scl::any_cast<std::string const &>(raw);  // без копирования
// scl::any_cast<std::string &>(raw);   // некорректно: только для чтения
```

Аргумент `std::any` преобразуется неявно, поэтому один и тот же `scl::any_cast`
читает и представление, и «голый» `std::any`:

```cpp
std::any boxed{text};
scl::any_cast<std::string>(boxed);   // через неявное преобразование в any_view
```

`scl::bad_any_cast` наследуется от `std::bad_cast` в любой конфигурации — никогда
от `std::bad_any_cast`, поэтому обработчик `catch (std::bad_cast const &)`
перехватывает его независимо от сборки, а сам тип не зависит от RTTI.

### Квалификаторы

Представление запоминает cv-квалификацию того, к чему было привязано, и приведение
обязано запрашивать все квалификаторы объекта: доступ может добавить
квалификацию, но не отбросить. `const` добавляется самим чтением, поэтому запрашивать на практике
приходится только `volatile`:

```cpp
int volatile sensor = 0;
scl::any_view const view{sensor};

scl::any_cast<int>(&view);                 // nullptr: отбросил бы volatile
scl::any_cast<int volatile>(&view);        // int const volatile *
scl::any_cast<int const volatile &>(view); // читает volatile-объект
```

Обратное направление разрешено всегда, поэтому по объекту без квалификаторов
проходит и запрос с `volatile`.

То же правило покрытия действует и для самого представления: если
`any_view` объявлено `volatile`, это тоже квалификатор, который обязан
покрыть запрос — независимо от квалификаторов наблюдаемого объекта:

```cpp
int number = 0;
scl::any_view volatile view{number};
scl::any_cast<int>(&view);          // nullptr: представление volatile
scl::any_cast<int volatile>(&view); // читает нормально
```

### Вычисление на этапе компиляции

Запросы идентичности — `type_name`, `type_key`, `has_value` и конструирование —
`constexpr` и вычисляются на этапе компиляции на базовом уровне C++20. А вот
`any_cast` на этом уровне выполняется во время выполнения — ровно как
`std::any_cast`.

Ограничение идёт от способа привязки, а не от стирания типа как такового.
Представление ссылается на lvalue любого типа, поэтому стереть его адрес оно
может только до `void const *`, а восстановление типизированного указателя из
`void` вычислимо на этапе компиляции лишь на компиляторах, реализующих P2738
(C++26). Стирание до общего базового класса на C++20 вычислимо и сейчас — но оно
требует выбирать компоновку хранимого, а это доступно только владеющему
хранилищу. Для представления над чужим объектом C++26 — самый ранний уровень,
на котором приведение свернётся.

### Идентичность через границу модуля

Приведение по прямой ссылке на объект сравнивает значения
[`scl::type_key`](../meta/type_key.md). Внутри одного модуля это сравнение
указателей; представление, пришедшее из другого модуля, сравнивается по
содержимому ключа — и это сравнение точное, в том числе для двух одноимённых
типов из анонимных пространств имён разных единиц трансляции: их различает
пер-TU дискриминатор ключа.

Два ограничения ключа переносятся без изменений:

- Тип, объявленный в блоке — локальный класс или тип замыкания, — вне контракта
  ключа и может ложно совпасть с одноимённым типом из пространства имён.
  Переносите такой тип на уровень пространства имён.
- Ключ не должен пережить модуль, который его создал. Освобождайте
  представления, созданные внутри разделяемой библиотеки, до её выгрузки.
