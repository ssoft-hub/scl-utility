# Ключ идентичности типа

Идентичность типа без RTTI, различающая одноимённые типы, объявленные в анонимных пространствах
имён разных единиц трансляции.

- Заголовок: `#include <scl/utility/meta/type_key.h>`

Содержание:
- [`type_key`](#type_key)
- [`type_key_of<T>`](#type_key_of)
- [`is_tu_local<T>`](#is_tu_local)

---

## type_key

Сравниваемый на равенство ключ идентичности типа: пара из строки имени, вычисленной на этапе
компиляции, и дискриминатора единицы трансляции, скрытая за инкапсулированным классом.

- Заголовок: `#include <scl/utility/meta/type_key.h>`
- Объявление:

```cpp
class type_key
{
public:
    type_key() = delete;
    type_key(type_key const &) = delete;
    type_key(type_key &&) = delete;
    type_key & operator=(type_key const &) = delete;
    type_key & operator=(type_key &&) = delete;

    constexpr std::string_view name() const noexcept;

    friend constexpr bool operator==(type_key const &, type_key const &) noexcept;
    // != синтезируется из ==
};
```

### Семантика

- `name()` — строка [`type_name<T>()`](type_name.md) идентифицируемого типа. Приватный
  дискриминатор равен `nullptr` для обычных типов (с внешним связыванием); для TU-локальных
  типов он хранит адрес объекта-якоря, приватного для включающей единицы трансляции, поэтому
  одноимённые типы из анонимных пространств имён разных единиц трансляции несут разные
  значения.
- Равенство сначала срабатывает по **идентичности адресов**: ключи живут в per-type константах
  (см. `type_key_of`), поэтому сравнение сохранённых ссылок сводится к одному сравнению
  указателей. Иначе — сравнение по содержимому: равны имя и дискриминатор. Для типов,
  объявленных в области видимости пространства имён, это не даёт ни ложных совпадений
  (одноимённые TU-локальные типы различаются дискриминатором), ни ложных отказов (внешний тип,
  используемый из исполняемого файла и разделяемой библиотеки, сравнивается по имени при
  нулевом дискриминаторе с обеих сторон — неслитые inline-инстанцирования на Windows равенство
  не нарушают).
- Ключ производит только `type_key_of<T>()`: члены приватны, конструктор по умолчанию удалён,
  изменяющего API нет. «Рукодельный» ключ, сочетающий имя одного типа с дискриминатором
  другого, существовать не может.
- Ключ — идентичность со ссылочной семантикой, поэтому он **некопируемый и неперемещаемый**
  (прецедент — `std::type_info`): копия молча теряла бы адресный быстрый путь и провоцировала
  хранение ключей по значению. Потребители держат `type_key const &` или `type_key const *`.
- Ключ намеренно **не упорядочен** (нет `operator<=>` и поддержки `std::less`): его
  идентичность включает адреса объектов, относительный порядок которых для несвязанных объектов
  не специфицирован и недоступен в константных выражениях. Поддержка хэширования отложена до
  появления реального потребителя.

### Время жизни ключа

Ключ — это представление модуля (исполняемого файла или разделяемой библиотеки), который его
породил: `name()` указывает в литерал сигнатуры этого модуля, а дискриминатор — в его якорь.
**Ключ не должен переживать породивший его модуль.** После `FreeLibrary`/`dlclose` указатели
повисают, а модуль, позднее отображённый по тому же базовому адресу, может даже «воскресить»
устаревший TU-локальный ключ до ложного совпадения со свежим, никак не связанным ключом.
Сбрасывайте сохранённые ключи при выгрузке породившего их модуля.

## type_key_of<T>

Возвращает ссылку на per-type `type_key`, идентифицирующий `T`.

- Заголовок: `#include <scl/utility/meta/type_key.h>`
- Объявление: `template <typename T> constexpr type_key const & type_key_of() noexcept;`

Ключ — per-type-переменная `inline constexpr`: каждое использование `type_key_of<T>()` для
внешнего `T` внутри одного модуля обращается к одному и тому же объекту, поэтому равенство с
сохранённой ссылкой — одно сравнение адресов. Ключ некопируемый, поэтому потребители, хранящие
ключи долговременно (обёртки со стиранием типа), держат `type_key const &` или
`type_key const *` на per-type-константу — ровно ту форму, которая сохраняет быстрый путь.

### Предусловие

`T` должен быть объявлен в области видимости пространства имён. Локальные классы и замыкания
вне контракта: компиляторы печатают их без надёжного маркера, и никакая compile-time-защита не
обнаружит нарушение. На Clang локальный класс печатается голым именем, поэтому его ключ
байт-в-байт совпадает с ключом одноимённого типа из области видимости пространства имён — два
действительно разных типа сравниваются равными:

```cpp
struct duck {};                     // область видимости пространства имён
int main() {
    struct duck {};                 // локальный класс — вне контракта
    // проходит на Clang: ложное совпадение с обычным внешним типом
    static_assert(scl::type_key_of<::duck>() == scl::type_key_of<duck>());
}
```

(GCC печатает `main()::duck`, MSVC — `struct main::duck`, они не совпадают.) Чтобы дать такому
типу корректный ключ, вынесите его в анонимное пространство имён той же единицы трансляции:

```cpp
namespace { struct duck {}; }             // корректный ключ
```

### Примеры

```cpp
#include <scl/utility/meta/type_key.h>

namespace { struct duck {}; }
struct goose {};

constexpr auto & anon_key = scl::type_key_of<duck>();
constexpr auto & ext_key  = scl::type_key_of<goose>();

static_assert(anon_key == scl::type_key_of<duck>());
static_assert(anon_key != ext_key);
static_assert(&scl::type_key_of<goose>() == &ext_key);  // один объект на тип
```

Одноимённые типы из анонимных пространств имён разных единиц трансляции дают ключи с равными
строками `name()`, но разными дискриминаторами — ключи не равны, что и требуется механизму
стирания типов перед обратным `static_cast` из стёртого состояния.

### Типичные сценарии

Хранилища со стиранием типа (обёртки в духе `any`, представления аргументов функций), которым
нужно восстановить типизированный указатель сравнением сохранённого маркера — без включения
RTTI и без неопределённого поведения, которое допускало бы сравнение только по строке при
коллизии анонимных пространств имён.

## is_tu_local<T>

Определяет, локален ли `T` для текущей единицы трансляции, то есть объявлен ли он в анонимном
пространстве имён — непосредственно или как компонент составного типа.

- Заголовок: `#include <scl/utility/meta/tu_local.h>`
- Объявление:

```cpp
template <typename T> struct is_tu_local;                    // : std::bool_constant<...>
template <typename T> inline constexpr bool is_tu_local_v;   // = is_tu_local<T>::value
```

### Семантика

Детекция выводит маркер анонимного пространства имён конкретного компилятора на этапе
компиляции — сравнивая рендер `type_name<T>()` TU-локальной пробы с внешней пробой той же
формы — и ищет его в отображаемом имени `T`. Выводятся два маркера, потому что MSVC печатает
маркер по-разному для типов верхнего уровня и типов, вложенных в аргументы шаблонов. Вывод
вместо жёсткого списка сохраняет работоспособность трейта на непроверенных компиляторах.

Маркер принимается в любом месте строки вне строковых и символьных литералов, поэтому составные
типы покрыты: указатель на TU-локальный тип, ссылка на него или специализация шаблона по нему
сами TU-локальны. Строковые и символьные non-type template-параметры печатаются внутри
литералов в кавычках (на MSVC — кодами символов), а содержимое литералов пропускается — NTTP,
содержащий текст маркера, не может ошибочно классифицировать внешний тип.

### Пример

```cpp
#include <scl/utility/meta/tu_local.h>
#include <vector>

namespace { struct duck {}; }
struct goose {};

static_assert(scl::is_tu_local_v<duck>);
static_assert(scl::is_tu_local_v<duck *>);
static_assert(scl::is_tu_local_v<std::vector<duck>>);
static_assert(!scl::is_tu_local_v<goose>);
static_assert(!scl::is_tu_local_v<int>);
```
